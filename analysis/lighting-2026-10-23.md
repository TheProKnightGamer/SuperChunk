# Lighting new chunks — 2026-10-23

With the GPU lighter to run (`analysis/gpu-small-batches-2026-10-22.md`), this pass looked at the CPU
side, starting with lighting. Lighting is ScalableLux's copy of Starlight
(`dev.superchunk.ca.spottedleaf.starlight`, unchanged from upstream apart from the Sable
frame-shift guard and the `chunkFutures` cleanup). Every change below is exact: the engine does the
same writes as before and skips only reads and queue entries whose result is already known.

## Where the time goes

JFR, r2048 GPU pregen, 22 workers: lighting new chunks (`StarLightInterface.lightChunk`) was 5.1% of
all worldgen CPU, about 1.1 ms per chunk. By call site, before and after this pass:

| share of all CPU | before | after |
|---|---|---|
| sky: propagation (`performLightIncrease`) | 1.51% | 1.13% |
| block: chunk-edge checks (`checkChunkEdges`) | 1.04% | 0.87% |
| sky: chunk-edge checks | 0.62% | 0.42% |
| block: light sources (`getSources`) | 0.58% | 0.17% |
| sky: column pass (`tryPropagateSkylight`, and the prune after it) | 0.42% | 0.49% |
| block: propagation | 0.42% | 0.37% |
| setup, emptiness maps, publish | 0.4% | 0.4% |
| **all lighting** | **5.06%** (1.07 ms/chunk) | **3.91%** (0.79 ms/chunk) |

`getBlockState` showed as 3.1% of all CPU, but most of that is attribution: compiled code records
lines only at calls, so samples in the propagation loop land on its one real call, the palette
lookup. Reading the sections' block storage ahead of time (a sequential pass over every cached
section) changed nothing, so cold block arrays are not the cost either.

## Changes

- **Sky column entries that can do nothing are dropped** (`SkyStarLightEngine#dropColumnNoOps`). The
  column pass queues every sky-lit block down each column, about 2,900 per chunk, each to send 15
  down and sideways. Most are open air whose neighbours are already 15, so the propagation reads
  them and discards them. The pass now records each column's lowest lit block, and an entry is kept
  only at that block, below a side neighbour's lowest lit block, or beside a block of a neighbouring
  chunk that is not yet 14 or 15. 66% of the entries go; the dropped ones would have done no write.
- **Light sources found from the palette** (`BlockStarLightEngine#getSourcesByPalette`). A section
  whose palette holds an emitter (lava, glow lichen, magma, amethyst) was scanned block by block,
  4,096 `PalettedContainer.get` calls and as many `getLightEmission` calls, about 2.3 sections per
  chunk. The scan now marks the palette ids that may emit (the test that already skips whole
  sections) and walks the raw bit storage, calling `getLightEmission` only on those blocks.
- **Edge-check reads the palette answers** (`StarLightEngine#getPaletteFlags`, per cached section,
  per update). Block light: in a section with no emitter, a block's emission is 0 without asking.
  Both: a neighbour's block is read only to see whether it can be conditionally opaque (slabs,
  stairs, snow layers), so in a section without one it is not read. Sky light: the block being
  checked matters only once a neighbour is bright enough to pass light into it, so it is read then.
  (The same lazy read for block light was slower: its upstream form returns right after reading an
  opaque block, and the lazy form read six neighbour nibbles first.)

Kill switches: `-Dsuperchunk.lighting.paletteSkips=false`, `-Dsuperchunk.lighting.skyColumns=false`.

## Exactness

Saved light cannot be compared between two runs: two r1024 worlds from the same jar differ in 4,612
of 15,625 interior chunks (`tools/lightdiff.py`), because which neighbours were lit when a chunk
was, and which later edge fixes reached disk, depend on scheduling. So the gate runs inside one
server: `-Dsuperchunk.lighting.verify=true` lights each new chunk twice from the same state, with
and without the shortcuts, and compares every sky and block nibble (state and data) of the chunk
and its eight neighbours, the chunk's emptiness maps and the filled-in emptiness changes. The run
without the shortcuts is the one kept. A chunk whose neighbours changed lit status between the
two runs is counted as unstable and not compared.

| r1024 GPU, `lighting.verify=true` | chunks | compared | mismatches |
|---|---|---|---|
| this build | 16,690 | 14,968 | **0** |
| null control (both runs without the shortcuts, `-Dsuperchunk.lighting.verifyFast=0`) | 16,690 | 14,572 | 0 |
| negative control (the column prune also dropping each column's lowest entry) | 16,690 | | 14,240 |
| forge-1.20.1 | 17,170 | 16,088 | **0** |

A first version of the gate had no unstable check and reported 5 mismatches in 16,690; with the check
the null control shows those were neighbours finishing between the runs.

## Cost

Light CPU per chunk (thread CPU time of `lightChunk`), r1024 GPU, 11 workers each, the upstream
engine (with the timer) and this build running at the same time, three pairs:

| | upstream | this build | |
|---|---|---|---|
| sky | 399 µs | 322 µs | −19% |
| block | 310 µs | 249 µs | −20% |
| total | 709 µs | 571 µs | **−19.5%** (every pair, −17..−22%) |

In one run on the final jar, everything off on every other chunk (`lightTimingAB=3`): 782 → 617
µs/chunk (−21.1%; sky −22.7%, block −18.9%); forge-1.20.1 902 → 707 (−21.6%). The column prune
alone is −18.9% of sky light, its border columns −5.4%. In the profile the source scan went from
0.58% to 0.17% of all CPU and the block edge checks from 1.04% to 0.87%.

Lighting is 3–5% of worldgen CPU in GPU mode (5.1% in the profile above, 2.9% in the pairs), so this
is worth about 0.6–1% of all CPU: below what process CPU per chunk resolves on this box (over two
sets of three such pairs, `cpu_ms_per_chunk` moved −2.1% and +0.7%). The light timer measures it
directly.

New: `-Dsuperchunk.debug.lightTiming=true` reports the thread CPU time of `lightChunk` per chunk at
server stop, sky and block apart. `-Dsuperchunk.debug.lightTimingAB=<bits>` also turns those
shortcuts off on every other chunk (a checkerboard) and reports the halves apart. That A/B compares
the new code with and without its shortcuts, not with upstream: it missed the slower lazy read
above, which both halves ran. The comparison with upstream is a jar with the timer and the
unchanged engine, run at the same time as the new one.
