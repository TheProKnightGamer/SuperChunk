# Ore placement — 2026-10-24

After lighting (`analysis/lighting-2026-10-23.md`), the next CPU item in GPU mode was ore placement
(`OreFeature`), the biggest single feature. SuperChunk already replaced `doPlace` with an
overhead-free copy of vanilla's (`MixinOreFeatureFast`); this pass changes what that copy and
`place` compute. Every change is exact: the same blocks are placed in the same order, with the same
random draws and the same reads and writes. Only work whose answer is already known is skipped.

## Where the time goes

JFR with `-XX:+DebugNonSafepoints` (line attribution in compiled code is otherwise off by a call),
r2048 GPU pregen, 22 workers, the two builds run back to back under the same machine load:

| share of all worldgen CPU | before | after |
|---|---|---|
| height check before each ore (`place`) | 2.94% | 0.39% |
| sphere loop: which blocks an ore covers | ~5.2% | ~2.7% |
| per block: read, target test, write | ~3.8% | ~3.0% |
| the spheres themselves (radii, overlap removal) | ~0.7% | ~0.6% |
| **all ore placement** | **14.0%** | **7.9%** |

CPU per chunk for those two runs went from 20.33 to 19.69 ms. A chunk makes about 253 ore calls;
about 94 of them reach `doPlace`, and each of those visits about 76 blocks.

## Changes

- **Height check** (`OreRuns#reaches`). `place` asks `level.getHeight(OCEAN_FLOOR_WG)` for each column
  of the ore's box until one reaches the box's bottom, and only then places. Most upper ores
  (90 upper-iron and 30 upper-coal attempts per chunk) are in the air, so all 81 or 121 columns are
  asked, each through `WorldGenRegion.getChunk` and the chunk's heightmap map. Now each chunk is
  looked up once, at the column vanilla would first look it up at. In a plain `ProtoChunk` the
  heightmap is read directly. A chunk whose highest column is below the box is not read at all. That
  highest column is kept on the heightmap with a copy of its raw words (36 longs), and used only
  while the words still equal the copy.
- **Rows instead of blocks** (`OreRuns#run`, `MixinOreFeatureFast#superchunk$placeRuns`). `doPlace`
  tests every block of each sphere's bounding box with a division, and checks a bit set for blocks
  an earlier sphere already took. The ore's spheres overlap heavily. Along one row, vanilla's test
  holds on one interval of blocks, because each step of it rounds monotonically in the block
  coordinate. So the interval's ends are estimated in closed form and confirmed with vanilla's test
  itself: both ends pass and the blocks beyond them fail. If that check does not hold, the row is
  tested block by block. The confirming tests multiply by `1 / r` first and divide only within
  1e-9 of the threshold, where the two could differ. The bits of taken blocks are kept in a plain
  `long[]` indexed z first. A row is then a range of bits, and its new blocks are the clear ones, a
  word at a time. This takes effect only after the spheres are drawn and every one of them is
  confirmed to stay inside the box (`OreRuns#spheresFit`). There, vanilla's own index is one-to-one,
  so a different one-to-one index gives the same answers. Vanilla's `place` always fits; other
  callers keep the previous loop.
- **Target memo**. When every target is a plain block or tag test (all vanilla ores), the tests'
  answer for a block state is kept for the rest of the call, for the last two states seen. The
  discard-on-air draw and the air check still run per block, as in `canPlaceOre`, in the same
  order.

Each change stands down when another mod hooks a method it bypasses (`ForeignHooks`): `place`,
`canPlaceOre`, the rule tests, `WorldGenRegion.getHeight`, `ChunkAccess.getHeight` and the heightmap
reads. Kill switches: `-Dsuperchunk.worldgen.oreHeightScan=false`, `.oreRuns=false`,
`.oreTargetMemo=false`. `-Dsuperchunk.worldgen.oreFast=false` turns off the whole replica as before.

Tried and dropped:
- **No division for a row's y term.** No faster.
- **Skipping rows whose blocks are all taken** before confirming their ends. No faster on the
  performance cores; 6% on the efficiency cores.
- **A pre-draw bound on the box.** My first version bounded the spheres before they were drawn,
  using the largest centre offset plus the largest radius. That refused vanilla's own boxes, because
  the two never occur together. The check now runs on the drawn spheres.

## Exactness

- `OreRunsTest` (a regression test, part of `check`):
  - 4M rows: `run` against a block-by-block scan, half of them built so the sphere's surface passes
    within a few ulps of a block centre;
  - 20M cases: the multiply-first test against the division;
  - 300k ores drawn like vanilla's `place` and `doPlace`: the whole fast loop against vanilla's,
    31.4M blocks, the same blocks in the same order.
- `-Dsuperchunk.worldgen.oreVerify=true` runs vanilla's column scan and vanilla's block loop next to
  every call, compares the answer and the order of blocks handed on, and recomputes every memo answer:

| r1024 GPU, `oreVerify=true` | height checks | placements | blocks | mismatches |
|---|---|---|---|---|
| this build | 4,209,348 | 1,556,672 | 118,571,643 | **0** |
| forge-1.20.1 | 4,307,084 | 1,572,635 | 122,233,778 | **0** |

Every block went through the target memo, and the heightmaps were read directly, in both.

## Cost

`-Dsuperchunk.debug.oreTiming=true` reports the thread CPU time of `OreFeature.place` per call at
server stop. Three pairs, r1024 GPU, 11 workers each, the same jar with the three shortcuts off (A,
the previous code) and on (B), run at the same time:

| | A (before) | B (after) | |
|---|---|---|---|
| ore µs per call, neo | 6.38 | 4.27 | **−33%** |
| CPU per chunk, neo | 25.11 ms | 24.44 ms | −2.6% |
| ore µs per call, forge-1.20.1 | 5.87 | 4.17 | **−29%** |
| CPU per chunk, forge-1.20.1 | 24.53 ms | 23.42 ms | −4.5% (noisy; the ore time itself is −0.43 ms) |

An earlier set of three neo pairs, the previous build's jar against this one, gave −3.3% CPU per
chunk. The machine was heavily loaded by other work during these runs (about 370 chunks/s against
about 900 alone).

`-Dsuperchunk.debug.oreTimingAB=<bits>` turns shortcuts off on every other chunk and reports the
two halves apart. With all of them (`7`), the neo halves were 28–33% apart; the height check alone
(`1`) was 0.97 µs of 5.19 µs per call.

The sphere loop alone, timed outside the game on spheres drawn like vanilla's, with ore sizes
weighted as a chunk tries them:

| µs per ore | vanilla's loop | this build |
|---|---|---|
| performance core | 4.1 | 2.1–2.7 |
| efficiency core | 5.4 | 3.0 |

What is left is mostly the per-block reads and writes (palette lookups and bit storage, spread
thin) and the row-end math.
