# Structure terrain (Beardifier) on the GPU — 2026-10-22

With the corner kernel hoisted (`analysis/gpu-corner-hoist-2026-10-21.md`), a GPU-mode pregen on
this box is CPU-bound: the GPU is busy about a third of the run. So this pass looked for CPU work in
GPU mode that the GPU could take, and found one: chunks with structures.

## Where the CPU time was going

JFR, r1024, 22 workers, GPU on (`[compact-ids]` default recipe): the noise stage was 9.2% of all
worldgen CPU, and 6% of it was the **hybrid** path. The decide kernel could not add the
beardifier (the density structures add so villages, ancient cities, trail ruins and trial chambers
sit on adapted terrain), so every block inside a structure chunk's beard box came back as a
sentinel, and the CPU decided those blocks with vanilla's per-block machinery. `Beardifier.compute`
alone was 4.3% of all CPU. 1,386 of 17,785 chunks (7.8%) took that path, at about 20 ms of CPU each
against about 1 ms for a fully consumed chunk.

## Change

- **Terms shipped with the aux.** `MixinStructureWeightSampler.superchunk$beardTerms` packs the
  chunk's pieces (box, ground delta, terrain adjustment) and junctions in `compute()`'s order;
  `CompactIds.captureAux` attaches them and `GpuBatchDispatcher` uploads each batch's terms
  (`aux[9]` = 2, offset and counts in `aux[18..20]`).
- **Summed in the decide kernel** (`sc_beard_run`, decide.cl), once per z-run: density =
  finalDensity + beard, in double, as the CPU adds it. Blocks outside the beard box are unchanged.
- **Lookups, not arithmetic.** Except BEARD_BOX, a term depends only on small integer distances, so
  the CPU fills tables of every term once (`superchunk$beardTables`: junctions, BEARD_THIN, BURY,
  ENCAPSULATE, 31,070 doubles), each computed by the same functions and factor `compute()` uses. A
  lookup is that term's double. BEARD_BOX (ancient cities) also depends on the piece's height and is
  computed in the kernel, op for op (vanilla `getBeardContribution`, `Mth.fastInvSqrt`, vanilla's
  `BEARD_KERNEL` floats).
- **Zero terms skipped** by integer range tests (each a range where the term is exactly 0.0; the
  sum is never -0.0, so a 0.0 term changes nothing).
- Chunks whose terms cannot be shipped (an unknown terrain adjustment, more than 65,536 ints, tables
  unreadable) keep the sentinel path, and `gridsAreDead` keeps their corner grids. Structure chunks
  summed on the GPU no longer need theirs read back. Kill switch
  `-Dsuperchunk.gpu.beardOnGpu=false`. A mod that hooks `Beardifier` already turns compact ids off
  (`BlockFillHooks`).

The first version computed every term in fp64 on the GPU. The replay below showed that cost
about 13 ms per 12 structure batches (6x the rest of the decide kernel): fp64 runs at 1/64 rate on
GA104 and each in-reach term was about 20 double operations. The tables removed nearly all of it.

## Parity

- **fp64 decide** (`gpu.decideFp32=false`), `compactIds=verify` (ships the CPU loop and compares
  every side effect of the consume path): neo r1024, 17,785 chunks, 1,748,336,640 blocks,
  1,386 structure chunks summed on the GPU: **0 mismatches**, every class. Forge r1024, 18,393
  chunks, 1.81B blocks, 506 structure chunks: **0 mismatches**.
- **Negative control:** the same run with the beard multiplied by 0.0 in the kernel: 871 chunks and
  325,361 blocks differ. The gate sees the beard.
- **Default fp32 decide**, r1024 verify, GPU beard vs the old CPU sentinels: the same 8 flipped
  blocks out of 1.75B in both (the known fp32 envelope); the structure blocks now decided in fp32
  added none.

## Device time

New tool: `-Dsuperchunk.gpu.dumpDecideTo=<dir>` dumps decide batches that hold a GPU-beard chunk
(program, noise state, corner buffer, every aux input); `tools/decidebench.c` replays program
variants on them interleaved and hashes the ids. 12 batches, 142 chunks, RTX 3070:

| Variant | ms (12 batches) | |
|---|---|---|
| no beard (control, not exact) | 2.29 | |
| beard, tables, per z-run (shipped) | 2.67 | bit-exact |
| beard, tables, per block | 2.88 | bit-exact |
| beard, fp64 arithmetic, per z-run (first version, other batches) | 15.8 vs 2.6 without | bit-exact |

In-game `[gpu-timeline]` decide numbers swing 30% between runs on this shared GPU and could not
separate these variants; the replay could.

## Throughput

Concurrent pairs (two servers at once, launch order swapped each pair, process CPU per chunk from
the harness), RTX 3070, i7-14700K shared with other jobs (about 13 of 28 threads busy):

| A/B | pairs | CPU ms/chunk | chunks/s | |
|---|---|---|---|---|
| same jar, `beardOnGpu` true vs false (fp64-arithmetic kernel), r1024, 10 workers, 6 GB | 4 | 24.99 vs 26.08 (−4.2%) | 301.9 vs 291.6 (+3.5%) | GPU beard won every pair on both |
| final jar vs PR #24 head (4fe461f), r768, 10 workers, 5 GB | 4 | 24.75 vs 25.71 (−3.7%) | 406.1 vs 396.0 (+2.5%) | CPU: 3 wins, 1 tie; cps: 3 of 4 |

The gain follows how many chunks hold structures (7.8% here at r1024): a modpack that adds
structures sends more chunks down the old CPU path, and on the GPU their cost is now near zero.

## Notes

- The run version keeps each block's terms in list order (`out[l]` per block), so it is the same
  sum; only the x and y range tests are shared.
- Forge 1.20.1 has no ENCAPSULATE and its `getBuryContribution(int, int, int)` halves y inside;
  its table builder calls that, the kernel is the same file.
