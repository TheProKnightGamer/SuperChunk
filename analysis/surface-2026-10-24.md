# Surface building — 2026-10-24

After ore placement (`analysis/ores-2026-10-24.md`), surface building (`SurfaceSystem.buildSurface`)
was the largest stage left on the CPU in GPU mode: about a fifth of worldgen CPU, as much as all
feature placement. Every change below is exact: the same blocks, writes, heightmap updates, fluid
post-processing marks and random draws, in the same order.

## Where the time goes

JFR with `-XX:+DebugNonSafepoints`, r2048 GPU pregen, 22 workers, this morning's build and this one
run back to back under the same machine load:

| share of all worldgen CPU | before | after |
|---|---|---|
| surface rules (`tryApply`), mostly near the surface | 8.1% | 4.3% |
| block writes (mostly stone to deepslate below y 0) | 5.2% | 4.4% |
| block reads, the stone-depth scan, the loop itself | ~9% | ~6.4% |
| **all surface building** | **22.3%** (4.83 ms/chunk) | **17.4%** (3.55 ms/chunk) |

CPU per chunk for those two runs went from 21.68 to 20.40 ms.

`buildSurface` walks every column from its top down to the bottom of the world. For each solid
block it updates the rule context (`updateY`), and for each stone block it runs the surface rules
(`tryApply`). The stone-depth scan reads ahead to the bottom of each run of solid blocks, so most
blocks are read twice. Vanilla's overworld rules, below the preliminary surface, are a bedrock
gradient at the floor and a deepslate gradient between y 0 and 8. The surface rules behind
`abovePreliminarySurface()` are skipped there. So about 130 blocks per column run a rule list whose
answer depends only on their height. Near the surface, the second rule asks whether the biome is a
badlands for every stone block, and each ask was a full fuzzy biome lookup.

## Changes

- **The rules below the preliminary surface, worked out once per rule tree**
  (`worldgen/DeepSurfaceRules`).
  - For each height, the table says what the tree returns there while `abovePreliminarySurface()`
    is false: nothing, one block state, or unknown.
  - Only that condition and vertical gradients outside their random band (and `not` of them) are
    read. Anything else, including any mod's own rule type, is unknown.
  - A block below the preliminary surface whose height has a known answer skips `updateY` and
    `tryApply` and gets the answer, which vanilla's loop writes as before. Skipping `updateY` is
    invisible to the next block's rules: it sets every field they read, and the conditions cached
    per height recompute because the context's counter moved on.
  - The table is logged once per tree. The overworld's is `-64 bedrock, -63..-60 unknown,
    -59..0 deepslate, 1..7 unknown, 8..319 nothing`. The nether's is bedrock at 0 and 127 and
    unknown between: its rules are not behind `abovePreliminarySurface()`. The end's is end stone
    throughout.
- **A copy of `buildSurface`, statement for statement, on a column held in an array**
  (`MixinSurfaceSystemFast`, `worldgen/SurfaceColumn`).
  - Reads are array loads, filled a section at a time the way `ProtoChunk.getBlockState` reads
    each block (`hasOnlyAir`, then the section's `getBlockState`).
  - The table above is applied inline.
  - Writes, the badlands and frozen-ocean extensions, the rule context and the biome lookups are
    vanilla's own.
  - It runs for an exact `ProtoChunk` without below-zero retrogen whose heightmaps
    `ProtoChunkWrites` can bind. When another mod's mixin is on `SurfaceSystem`, its block column,
    or the chunk reads it replaces, vanilla's method runs instead. That method then still uses the
    two shortcuts below and the table (through `@Redirect`s on `updateY` and `tryApply`).
- **Column memo, a section at a time** (`MixinSurfaceColumnMemo`, the path when the copy stands
  down). A miss reads the column's 16 blocks of that section. Its two hooks are now `@Redirect`:
  - a `@WrapOperation`'s call to the original passes its arguments as an array, every block;
  - for the table hooks that boxing cost more than the rules they skipped.
- **Heightmap updates that cannot change anything are skipped** (`ProtoChunkWrites#setInColumn`).
  `Heightmap.update` returns at once for a block at or below two under the column's value, which
  is where every deepslate write lands. The column's value per heightmap is kept for the column and
  read again whenever an update changes it.
- **Uniform biome cells** (`MixinBiomeManagerQuartCache`, `BiomeQuartCache`'s cell table).
  - `getBiome` returns one of the 8 corner quarts of the block's 4×4×4 zoom cell, whichever scores
    nearest. Where all 8 hold the same biome, it is that biome without scoring.
  - Each cell's answer is kept per region next to the quarts.
  - Only for the surface rules' lookups: they walk down columns and come back to the same cells.
    Placement filters ask once per cell, and there the 8 reads cost more (that regressed features
    by about 2.5% of CPU before it was limited).
  - The corners are read only within the chessboard radius where the region's generation step
    guarantees biomes, because a `getNoiseBiome` beyond it throws where vanilla, reading only the
    winning corner, might not. On 1.20.1 it never throws.
- **Biome test memo** (`MixinSurfaceBiomeConditionMemo`). A bound biome condition keeps its
  answer for the last biome holder it saw. `Holder.is(Predicate)` tests the holder's fixed key
  against the condition's fixed biome set, and a condition belongs to one chunk's rule context.

Each stands down when another mod hooks what it bypasses (`ForeignHooks`, `MixinTargetScan`).
Kill switches:
- `-Dsuperchunk.worldgen.fastSurface=false`
- `.deepSurfaceRules=false`
- `.surfaceColumnMemo.sections=false`
- `.biomeUniformCells=false`
- `.surfaceBiomeTestMemo=false`

`.surfaceColumnMemo=false` and `.leanSurfaceWrites=false` turn off the older two.

## Cost

`-Dsuperchunk.debug.surfaceTiming=true` reports the thread CPU time of `buildSurface` per chunk.
Three concurrent pairs, r1024 GPU, 11 workers each, the same jar with today's shortcuts off (A) and on
(B), before the biome test memo and heightmap skip were added:

| | A | B | |
|---|---|---|---|
| surface µs per chunk | 3,644 | 2,673 | **−26.6%** (every pair −25..−29%) |
| CPU per chunk | 23.83 ms | 22.96 ms | −3.6% |

This morning's jar against this one, three concurrent pairs: CPU per chunk 24.20 → 23.08 ms
(**−4.7%**), chunks/s +3.5..+5.6%. With the older memo and lean writes off too, the final build's
surface time is 4,041 → 2,491 µs per chunk (r1024) and 4,108 → 2,639 (all three dimensions). Forge:
4,383 → 3,330. The machine was heavily loaded by other work throughout (load 30–60).

**With the GPU off**, lighting (`analysis/lighting-2026-10-23.md`), ores and surface together, against
the build before them (`c521175`):

| GPU off | before | after | |
|---|---|---|---|
| CPU per chunk, three concurrent r1024 pairs (11 workers each) | 30.83 ms | 28.44 ms | **−7.8%** (every pair −7..−8%) |
| chunks/s, r2048 alone (22 workers), whole run | 628 | 689 | **+9.6%** |
| chunks/s, r2048 alone, 20% to 90% of the task | 675 | 751 | **+11.3%** |

The r2048 legs ran old, new, new, old at load 43–54 from other work, so their absolute rates are
well below an idle box. With the GPU off the same gates held: `surfaceHash` everything off vs on
over r512 overworld, r192 nether and end (6,443 chunks, 0 mismatches), `oreVerify` (441,609
placements, 0) and `lighting.verify` (5,524 chunks, 0).

`-Dsuperchunk.debug.surfaceTimingAB=<bits>` turns shortcuts off on every other chunk. It overstated
here: the A/B showed −23% for what concurrent kill-switch pairs put at −9..−18%, likely because both
paths stay hot in one JIT. The per-piece A/Bs (11 workers) were uniform cells −6.7%, the table −11.6%
and section reads −7.6% of surface time.

Tried and dropped: a per-cell uniform check for every `getBiome` caller (the regression above), and
the table through `@WrapOperation` hooks (their argument boxing was 5.6% of all CPU).

## Second pass: the deep part of each column, and the stone depth below

After the first pass, a GPU-off profile of the pushed build put surface building at 13.0% of worldgen
CPU: the rules near the surface 3.2%, the deep answers' writes 2.9%, the stone-depth scan 3.3%, the
walk's own reads 1.6%. Two more exact changes:

- **The deep part of each column, a section at a time** (`worldgen/DeepSurfacePass`).
  - `DeepSurfaceRules` now also answers inside a vertical gradient's random band: the answer there is
    "this if the gradient holds, else that", drawn per block by vanilla's test (through
    `FirstPositionalFloat`, as `MixinSurfaceGradientRandom` already does). The overworld's table has
    no unknown heights left: `-64 bedrock, -63..-60 bedrock_floor ? bedrock : deepslate, -59..0
    deepslate, 1..7 deepslate ? deepslate : nothing, 8..319 nothing`.
  - So below the preliminary surface the walk only replaces stone with the table's answer. Each
    column is now walked down to the highest of: the preliminary surface, the lowest unknown height
    and the column's heightmaps. The rest waits until the last column is done, then:
    - A section where every column leaves every height to the pass, and every height answers the
      same state, swaps the palette entry of stone for that state. The storage is untouched, so
      every stone becomes deepslate at once. Sections -3 to -1.
    - A section where most heights answer one state and the others always give a state swaps the
      same way, then writes the other answers. Section -4, the bedrock floor.
    - Any other section writes each stone block that has an answer. Section 0, heights 0 to 7.
    - Sections whose answers are all nothing, or stone itself (the end's end stone), aren't read.
  - Why the later order changes nothing:
    - Nothing else in the pass touches these blocks after the walk: the extensions stay at or above
      the preliminary surface, and no rule reads blocks.
    - The answers are solid and fluid-free, so they leave no post-processing marks.
    - Answers and stone both count in every heightmap the pass updates, and every height done here
      is below the column's heightmaps when its walk starts. A heightmap only moves down to the
      highest counting block left, which these stay, so the walk's own writes here never moved a
      heightmap either.
    - Only the in-memory palette order differs, and saving repacks it.
  - A swap keeps the section's counters and Lithium's block tracking (`trackBulk`). It stands down
    where another mod hooks section or palette writes; then the pass writes block by block.
- **The stone depth below, only as far as the rules can tell apart** (`worldgen/CeilingDepth`).
  - The walk scanned from the top of each solid run to its bottom, often tens of blocks, to pass
    `stoneDepthBelow` to `updateY`. Its only reader is a ceiling stone-depth check, which asks
    whether that depth is at most `1 + offset` (plus the surface depth if it adds it).
  - So a block reads at most the largest such limit below it, and passes the exact depth if the run
    ends within it, else the limit plus one. Every check gives the same answer either way.
  - The overworld's only ceiling check is `ON_CEILING`, limit 1: one block below. The nether's
    `UNDER_CEILING` adds the surface depth. The end has none.
  - Only for trees made entirely of vanilla's rule and condition classes, none hooked by another
    mod, and no ceiling check with a secondary depth range (its limit depends on another noise).
- A fix on the way: the foreign-mixin check stopped at the first class never loaded and missed any
  class after it in the list (`MixinTargetScan.foreignMixinIfLoaded`). Its probe now covers every
  vanilla rule and condition class.
